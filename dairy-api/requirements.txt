# The MCP server mounted at /mcp (ADR 016), and the client the deployment check
# drives it with.
#
# Bounded below AND above, and the upper bound is the load-bearing half.
# `mcp>=1.26` resolved to 2.0.0 on a clean install, 2.0 moved FastMCP to
# MCPServer under a different module, and the image built, shipped and died at
# import with ModuleNotFoundError -- while every test on a development machine
# holding 1.26.0 passed. pip only re-resolves on a fresh install, so nothing
# short of a container build could see it.
#
# `<2` is what the SDK itself prescribes for this situation. Its migration
# guide: "If your package depends on `mcp`, keep a `<2` upper bound until
# you've migrated." The same note records that the v1.x line keeps receiving
# critical bug fixes and security patches -- which is why the bound is a range
# rather than `==`. An exact pin closes the 2.0 hazard and closes the route to
# a 1.x security patch with it, and that second cost falls due exactly when
# there is no time to pay it.
#
# Moving to 2.x is a real migration, not a repin, and ADR 018 records why this
# project is not doing it yet. FastMCP was RENAMED to MCPServer rather than
# deleted, so the eventual move tracks a rename; the cost is elsewhere --
# transport settings leave the constructor, camelCase fields become snake_case
# across the tests and check_deployment.py, and httpx gives way to httpx2.
mcp>=1.26,<2
pytest>=7.0
pytest-asyncio>=0.21
